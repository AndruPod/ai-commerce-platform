# After: connected prototype experience

This folder holds **our connected prototype's answers** to the [baseline queries](../baseline/queries.md),
produced by the assistant at `POST /ai/chat`. That assistant answers only through tool calls into the
deterministic commerce layer. It is kept separate from the **Gemini baseline** in `../baseline/`.
Never edit, overwrite or regenerate baseline files from here.

## Before vs after

"Before" is signed-out Google Gemini Flash-Lite on 2026-10-04 ([screenshots and notes](../baseline/README.md)).
"After" is the connected prototype: the latest run [`run-2026-10-04-v5.md`](run-2026-10-04-v5.md)
(gpt-5-mini) plus the UI screenshots in [`../demo/`](../demo/). Gemini's X1/X2 compare with the
prototype's X1/X4 (same intent, slightly different wording; see [`queries.md`](../baseline/queries.md)).

| Area | Before (Gemini, observed) | After (connected prototype) |
|---|---|---|
| **Product retrieval** | Moves between a "1-Year Ballet Club For Skaters", a self-paced "12-Month Ballet Course", flexibility courses and private practice. B3 never names the target product. | Every run resolves "Victory Skating" / "VSA" to the single *1-Year Online Ballet Club* (`search_products` → `get_product`). No other product is mentioned, and the e2e suite proves product isolation. |
| **Audience** | B4 steers advanced students and professionals away from the group program towards private lessons. | B4 answers that the program is explicitly open to advanced students and professionals, taken from the product's audience levels. |
| **Pricing and provenance** | "$499 per year"; $179–$199 explained as promotional or original pricing with no supporting source; no awareness of the checkout mismatch. | "$499.00 (package total)", with no per-year restatement in v5 B5/B6/X4. The $179/year is described as what a captured checkout showed, conflicting and unresolved, without choosing between them. The UI shows both values from API data. |
| **Schedule and dates** | Classes "every Sunday"; for November 6 the user is sent to "the next upcoming Sunday session". | `check_date` is called. November 6 is a Friday, not a class day. The next **candidate** session is Saturday November 7, 19:00 UK time, marked not guaranteed because exception data is missing and the timezone is an unconfirmed assumption. |
| **Enrollment availability** | "Yes, absolutely!" / "Yes, you can enroll", stated as fact. | "Open" is reported, usually with the qualifier that it is prototype configuration not confirmed by VSA (v5 X1, X4, X5). It is kept separate from schedule and payment. Gap: v5 B6 says "open (per current data)" without that qualifier; the Enrollment panel always shows "Open*" with the note. |
| **Access period** | Described as an ongoing "subscription" / "continuous online access". | 12 months of access. The start and end rules are reported as not specified. |
| **Requirements and onboarding** | Equipment list (shoes, jump rope, mat, step platform) and onboarding emails within 24–48 hours. | "Participation/equipment requirements are not provided." No onboarding claims. |
| **Checkout / transaction safety** | Step-by-step guide to "proceed to checkout … complete your payment", with no warning. | The checkout is blocked by `PRICE_CONFLICT`. The backend returns `CHECKOUT_UNAVAILABLE` and no `CHECKOUT` action. The URL is withheld by the API (`url: null`, `urlWithheld: true`) and redacted if the model writes one. The UI shows "Verification required" with a disabled payment button. v5: blocked URL leaked in 0 of 16 turns. |

**Caveats.** Gemini had no access to our data, so part of the gap is information access rather
than reasoning. The comparison shows what grounding adds, not that one model is "smarter". The
prototype answers are non-deterministic; compare several runs (v1–v5 below). Remaining wording
issues in v5: occasional internal terms such as "authoritative" or "canonical timezone", the
unqualified "open" in B6, and a duplicated "$" in X5.

## How to capture a run

Prerequisites: Postgres running, `pnpm db:migrate && pnpm db:seed`, and `OPENAI_API_KEY` in `.env`
(optionally `OPENAI_MODEL`).

```bash
pnpm eval:ai -- --out docs/after/run-YYYY-MM-DD.md
```

The script uses timezone `Europe/London` (override with `EVAL_TIMEZONE`) and has two sections:

- **Section 1, independent:** each query is a fresh conversation (no history).
- **Section 2, conversational:** the following five turns, with history passed between them,
  including each assistant turn's `context.productSlugs`:
  1. "I'm interested in the VSA 1-Year Online Ballet Club."
  2. "How much is it?"
  3. "Do I need ballet shoes and a mat?"
  4. "Can I join around November 6, 2026?"
  5. "How do I enroll?"

For every turn it writes:

- the response **verbatim**;
- every tool call, with its validated arguments, success/error code and duration;
- the backend-built `actions` and the returned `context`;
- two automated heuristics: *internal terms in prose* and *ungrounded tool arguments*. These are
  indicators only; read the responses as well;
- the model name and capture timestamp in the header.

Section 1 queries:

- **B1–B6:** the six baseline queries, with wording identical to `../baseline/queries.md`.
- **X1:** "I'm free on November 6, 2026. Can I join the annual ballet program around that time?"
- **X2:** "Do I need ballet shoes and a mat?"
- **X3:** "Is the program $3 per class?"
- **X4:** "How do I enroll and pay for the VSA annual ballet program?"
- **X5:** "Is the checkout price the same as the advertised annual program price?"

You can also capture a single query manually:

```bash
curl -s localhost:3001/ai/chat -H 'content-type: application/json' \
  -d '{"message":"Does VSA have online ballet classes for complete beginners?","timezone":"Europe/London"}'
```

## Rules

- Use exactly the same query text as the baseline.
- Do not edit responses, and do not re-run a query to pick a better answer. If you re-run,
  keep every run as its own file.
- Write observations in a separate section or file, never inside the verbatim response.

## Review checklist (per query)

| Check | Expected from the connected prototype |
|---|---|
| Brand resolution | "Victory Skating" / "VSA" resolved to Victory Skating Academy (`search_products` → `businessResolution`) |
| Product isolation | Only the 1-Year Online Ballet Club; no private lessons or monthly plans mixed in |
| Price | $499 USD annual package (PACKAGE_TOTAL); **no** payment schedule claimed; "$3/class" never confirmed; the derived ≈$10.40 never presented as a price |
| Included | 48 live group classes, 60 minutes, coach Emilia, 12-month program (all taken from `get_product`) |
| Audience | Beginner through professional, from the audience levels |
| Enrollment | OPEN described as demo configuration (PROTOTYPE_CONFIG, UNCONFIRMED), not as confirmed by VSA |
| Dates (X1) | Uses `check_date`; Nov 6 = Friday, not a class day; Nov 7 = next *candidate*; exceptions not confirmed; no guarantee |
| Requirements (X2) | Says requirements are not confirmed in the product data; no invented equipment |
| Checkout | No link and no CHECKOUT action (checkout captured but blocked by a price conflict). Explains the conflict between the $499 offer and the $179/year checkout without choosing either; `CHECKOUT_UNAVAILABLE` action present |
| Grounding | Every factual claim traceable to a tool call in the trace |
